## DOM-006 — Measure a 1.5 GB push from a runner and that a first push comes out public

- **Status:** open
- **Priority:** P1
- **Effort:** S
- **Source:** the operator's ruling 6 of 2026-10-27: "no tokens are necessary, the mirror archlinux agent did everything using actions own tokens at runtime, didn't even need me to manually make any packages public, it did that on its own too". Design A section 13 and design B section 11 list every GHCR write as unmeasured.
- **Problem:** the design writes parts of up to 1 GiB and raw chunks of up to 4 GiB with the workflow's own `GITHUB_TOKEN`, and counts on each new package coming out public with no manual step. Nothing in this repository has written to GHCR. A wrong premise here breaks every later push.
- **Premise:**
  - READ mirror-archlinux `docs/measurements.md` (GHCR table): 10 GB per layer and a 10-minute upload limit are documented. A single push ran at up to 34 MB/s (2026-10-13, the first run). 299 of 299 pushes read back on the first try. Pushes got 429 `toomanyrequests` ("allowed: 2000/minute") at 4 targets x 3 shards x 6 pushes on one token (2026-10-14).
  - READ mirror-archlinux `docs/measurements.md`: "a package that `GITHUB_TOKEN` creates from this public repository reads anonymously" (2026-10-14). READ mirror-archlinux `README.md` ("Add a target"): "If the package is private, the run opens `visibility-<target>` ... GitHub has no API to change the visibility."
  - MEASURED `gh issue list --repo pkgforge-dev/mirror-archlinux --state all --search visibility --json number,title,state --limit 20` 2026-10-27T08:22:42Z: printed `[]`. So no `visibility-` issue was ever opened there, and its packages came out public.
  - MEASURED `curl -sS -D - -o /dev/null -H 'Authorization: Bearer QQ==' -H 'Accept: application/vnd.oci.image.manifest.v1+json' https://ghcr.io/v2/pkgforge-dev/mirror-archlinux/x86_64/core/manifests/latest` 2026-10-27T08:22:46Z: `200 OK`, `Content-Length: 1598`.

MEASURED `gh api repos/pkgforge-dev/domains.pkgforge.dev/actions/permissions` 2026-10-27T08:34:25Z: Actions enabled, all actions allowed, default workflow permission `write`.

  - READ mirror-archlinux `docs/design.md` ("Running outside GitHub Actions"): a package first pushed from outside a workflow is not linked to the repository, and the workflow token can never write to it.
  - READ mirror-archlinux `docs/measurements.md`: oras 1.3.4 keeps the `created` annotation it is given, so two writers that pass the same value push the same manifest digest (3 of 3, 2026-10-14). The default `created` is the push time.

  - **Workflow.** `.github/workflows/measure-push.yml`: `workflow_dispatch` with inputs `size_mb` (default 1536) and `layers` (default 0), which reach the job through `env`, never through a `run:` string. `permissions: {}` at the top, `defaults.run.shell: bash`. One job `measure-push`: `runs-on: ubuntu-24.04`, `timeout-minutes: 40`, permissions `contents: read`, `packages: write` and `issues: write` (a push of a first package is followed by the anonymous-read check that raises `visibility-<package>`). **Pinned actions:** `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1` with `persist-credentials: false` (the pin of mirror-archlinux's `ci.yml` at commit 669ac725f8081445c164113f2ed092533de112e2), `actions/setup-node` with `node-version-file: .node-version`, and `actions/upload-artifact` with `overwrite: true` for `push-result.json`; resolve the last two with the recipe of DOM-013 (`gh api repos/OWNER/NAME/releases/latest`, then `gh api repos/OWNER/NAME/git/ref/tags/TAG`) and keep the `# vX.Y.Z` comment. Steps: the pinned checkout, `scripts/install-oras RUNNER_TEMP/bin` (copy the script from mirror-archlinux unchanged; DOM-014 keeps it and adds its test), generate `payload.bin` from `/dev/urandom` (incompressible, the worst case), log in with `oras login ghcr.io -u "$GITHUB_ACTOR" --password-stdin` into a registry config under `RUNNER_TEMP` that the job removes at the end.

If only the read fails, keep the namespace and open the question "make the package public" with the exact settings link. The operator ruled that it needs no manual step, so a failure is a finding, never an expected step.
- **Depends on:** none
- **Resources:** one GHCR package, `ghcr.io/pkgforge-dev/domains.pkgforge.dev/probe`. It has no undo. By the operator's ruling 5 of 2026-10-27 nothing is ever deleted from GHCR, so the probe stays. It holds about 6 GiB. State this in `docs/resources.md`.
- **Prove:** `node scripts/measure/push-summary.mjs --run RUN_ID` prints `PASS push-1536m-under-600s`, `PASS push-4096m-under-600s`, `PASS layers-at-least-128`, `PASS anonymous-read` and `PASS second-push-with-token`. RUN_ID is the run of `measure-push.yml`.

## DOM-007 — Measure Worker Range reads from GHCR: cold, warm, and 20, 50 and 100 requests a second

- **Status:** open
- **Priority:** P1
- **Effort:** M
- **Source:** design A section 13 and design B section 11 Phase 0 items 1 and 3: every read measurement so far came from a laptop in Nepal, none from a Worker.
- **Problem:** every query reads a manifest, follows a blob's 307 to a signed URL, and range-reads a block. The design counts on a cold read of about two small range reads a pack and on anonymous reads surviving 100 requests a second from Cloudflare's egress. Nothing measures either from a Worker.
- **Premise:**
  - MEASURED 2026-10-27T05:36:29Z to 05:37:47Z (design B M7, `docs/research/2026-10-27-design-b/scripts/burstsum.sh`, result `docs/research/2026-10-27-design-b/results/ghcr_burst.txt`): 300 of 300 anonymous manifest GETs of `ghcr.io/v2/pkgforge-dev/mirror-archlinux/x86_64/core` at concurrency 50 gave 200 (median 0.45 s, p95 0.53 s, max 7.6 s). No 429 at about 6 requests a second from one address. 198 of 200 blob 307 requests succeeded; 2 failed to connect; p95 was 15 s. That run came from a multi-WAN laptop, so the tail may be the client.
  - MEASURED 2026-10-27T05:23Z (design A M11): manifest GET 0.531 s. The blob 307 step took 0.40 to 0.51 s. The signed URL is on `pkg-containers.githubusercontent.com`, served by `Windows-Azure-Blob/1.0`, with `Accept-Ranges: bytes`, and it expired about 7 minutes after issue (`se=05:30:00Z`, issued 05:23Z). Range reads: 1 KB in 0.68 s, 64 KB at offset 25 MB in 0.94 s, the last 367 B in 1.57 s, all 206. Design B saw `se` 8.7 minutes ahead and a 206 in 0.57 s.
  - MEASURED 2026-10-27 (design A M11, design B M7): through the sibling project's generic Range route, three runs took 2.39, 1.63 and 1.54 s (`x-web-cache: miss`), and a Range read took 1.8 to 3.0 s from Kathmandu. That route lists tags, reads the manifest and reads the blob, so it is a ceiling, not the target.
  - READ mirror-archlinux `docs/measurements.md`: 30 manifest GETs at once all gave 200 (2026-10-14). A 200 carries no `RateLimit` or `Retry-After` header. The only documented limit is on writes (2,000 requests a minute per token).
  - READ mirror-archlinux `docs/worker.md` ("Caching", "Limits"): the Worker caches `loc`, `man`, `blob` and `token` entries in the Cache API. A signed URL lives until its `se` minus 120 s and at most 600 s. A manifest by digest lives 1 year, `latest` 30 s. `[limits] cpu_ms = 50`. A subrequest deadline of 10 s. One answer costs at most three cache lookups and two GHCR subrequests.
  - READ mirror-archlinux `worker/src/index.js` lines 212 to 376: `send`, `bearerRealm`, `tokenKept`, `tokenNew`, `ghcr`. `docs/research/reference/ghcr.ts` is the same code in the sibling project's form.
- **Approach:**
  - **Route.** Add `probes/worker/src/range.ts` and the route `/range` to the probe Worker that DOM-061 deploys. Query: `tag`, `repo`, `offset`, `length`, `cache` (`none`, `signed`, `block`). Steps: GET the manifest with `Authorization: Bearer QQ==` and the OCI `Accept` list; pick the layer; GET the blob with `redirect: 'manual'` and read `Location`; GET the signed URL with `Range: bytes=OFFSET-END`. `cache=signed` keeps the signed URL and the manifest in the Cache API under the TTL rules above. `cache=block` also keeps the block under the key `digest/offset-length`.
  - **Answer.** JSON with the status of each step, its milliseconds, the subrequest count, `cf-ray` (the data centre), and the first and last bytes read. The Worker reports a cache state only when it read that cache.
  - **Target blob.** The 1.5 GB blob of DOM-006 (`probe:size-1536m`). Also the 199 MiB blob of mirror-archlinux that its `docs/measurements.md` used on 2026-10-14, as a second repository.
  - **Load.** `scripts/measure/range-load.mjs --url URL --rps N --seconds 60 --mode cold|warm --expect 206`. It is open loop: it starts requests on a clock, whatever the earlier ones do. `cold` asks a new random 25 KB block each time. `warm` asks 50 fixed blocks. It runs at 20, 50 and 100 requests a second for 60 s each, once from the operator's machine and once from a GitHub runner (`measure-range-load.yml`: `workflow_dispatch` only, `permissions: {}` at the top, `defaults.run.shell: bash`, one job `measure` with `contents: read` only, and the pinned actions of DOM-004 including `actions/checkout@3d3c42e5aac5ba805825da76410c181273ba90b1 # v7.0.1` with `persist-credentials: false`). It prints counts of 206, 429, 5xx and other, p50, p95 and max latency, and the subrequests a request made.
  - **Cold and warm single reads.** 30 requests of each size (1 KB, 25 KB, 64 KB, 1 MB), cold then warm, from the same two places.
  - **Result.** `docs/research/measure/DOM-007/result.json`, plus a table that replaces the [E] latencies in `docs/architecture.md` section 4.3.
- **Decision:** if 429 or a 5xx rate above 1% appears at 50 requests a second or more, the design caches more (blocks and indexes in R2, entry DOM-031) and the Worker coalesces concurrent reads of one block per isolate. The 5 GB cap stays. If GHCR throttles anonymous reads at any rate the Worker needs, the Worker's cold path moves to the root, the indexes and hot packs in R2 first. Record which.

## DOM-008 — Measure deflate-raw decode CPU in workerd

- **Status:** open
- **Priority:** P1
- **Effort:** S
- **Source:** design B section 2.4 item 3 and section 11 item 2; design A section 12 ("Block decode CPU in Workers is unmeasured"). The design in `docs/architecture.md` section 4.4 chooses `deflate-raw` because Workers decode it with `DecompressionStream`.
- **Problem:** every cold read decodes at least one block in a Worker whose CPU limit is 50 ms (mirror-archlinux's setting). If `DecompressionStream('deflate-raw')` is missing, or costs several milliseconds a block, the format needs another codec or another block size before the first pack is published (DOM-022 and the adapters). The pack format of DOM-017 names its codec and block size in its own header, so DOM-017 does not wait for this entry: this entry changes defaults, not the layout.
- **Premise:**
  - MEASURED 2026-10-27 06:27Z (design B M10, `docs/research/2026-10-27-design-b/scripts/blockenc.mjs`, results `docs/research/2026-10-27-design-b/results/blockenc_1024.json`, `blockenc_4096.json`, `blockenc_16384.json`): 32,554,702 distinct names of THC's 2026-10-26 file, sorted by reversed labels, front coded, deflate level 9 per block. 1,024 names a block: 6.26 B a name, 31,792 blocks. 4,096: 6.04 B, 7,948 blocks (196.6 MB). 16,384: 5.93 B, 1,987 blocks. Front coding alone: 11.98 B a name (389.8 MB). Brotli 9 gave 6.00 B and zstd 12 gave 6.07 B at 4,096, within 1.5% of deflate.
  - READ design B section 2.4 item 3: the author did not run `DecompressionStream('deflate-raw')` in workerd.
  - READ mirror-archlinux `docs/measurements.md` ("Cloudflare Workers"): `limits.cpu_ms` is a cap per invocation, enforced on Cloudflare only. Workers Paid includes 30 million CPU-ms and bills $0.02 per million after that (design B section 2.3).
  - ⚠ In workerd, `Date.now()` and `performance.now()` advance only after I/O. A timer around a decode reads 0. CPU must come from the platform's own account.
  - READ design B section 2.3: a Worker holds 128 MB and 6 concurrent connections. A decode of one block takes at most about 64 KB of memory.
  - THC samples: `curl -sS -r 0-20000000 https://cs2.ip.thc.org/2026-10-26.txt.gz` returns 206 (design A M1, Range supported). It holds a truncated gzip member of about 2 million names. `gzip -dc` prints names, then an error at the cut.
- **Approach:**
  - **Sample pack.** `scripts/measure/make-sample-pack.mjs` reads names from stdin, normalises them (lowercase, strip wildcards, reverse labels as `docs/research/2026-10-27-design-b/scripts/revlabel.mjs` does), sorts them bytewise, front codes them with the record layout of `blockenc.mjs` (`varint(shared)`, `varint(suffix_len << 2 | flags)`, suffix bytes; flags 1 exact, 2 wildcard), and writes blocks of 1,024, 4,096 and 16,384 names, each compressed with `zlib.deflateRawSync` level 9. It writes the blocks and a small offset table. Use `node:zlib` on the writer side. This entry does not need DOM-017.
  - **Route.** Add `probes/worker/src/decode.ts` and the route `/decode?blocks=N&per=4096` to the probe Worker of DOM-061. It reads N blocks of the sample from the probe's R2 bucket, decodes each with `new Response(blob.stream().pipeThrough(new DecompressionStream('deflate-raw')))`, parses the records, and answers a count and a checksum. `/decode?rows=1000` builds a response of 1,000 JSON rows from the decoded blocks.
  - **CPU.** Read CPU from the platform. First choice: Workers Logs (`observability` enabled in the probe's `wrangler.toml`), field `$workers.cpuTimeMs` of each invocation. Second choice: `npx wrangler@4.150.0 tail --format json` and the invocation's CPU field. Record which of the two gave numbers. Third choice, which never fails: set `[limits] cpu_ms` to 5, 10, 25 and 50 in four deployments of the probe and find the largest `blocks` that does not end with error 1102 ("exceeded CPU"). Run 200 requests at each of `blocks=1, 4, 16` and `per=1024, 4096, 16384`. Report p50 and p99 CPU per block and per 1,000 names.
  - **Correctness.** `node scripts/test.mjs probes/worker --name "decode"` runs the same route in local Miniflare workerd against a fixture pack and checks the decoded names equal the input.
  - **Compatibility date.** Record the lowest `compatibility_date` and flags under which `deflate-raw` works, and write it in `docs/format.md` (DOM-017 creates it; if it does not exist yet, DOM-017 reads this entry's result file).
  - **Apply the verdict.** If the Decision below keeps `deflate-raw` at 4,096 names a block, change nothing. If it picks 1,024 names a block or the `gzip` codec, change the two default constants of `packages/pack` (`DEFAULT_RECORDS_PER_BLOCK`, `DEFAULT_CODEC`) and the table of `docs/format.md` in the same commit as the result file: both are fields of the part header, so a pack written earlier still reads.   - **Result.** `docs/research/measure/DOM-008/result.json` and a table for `docs/architecture.md` section 4.4.

That leaves 35 ms of the 50 ms for JSON and the rest. ## DOM-017 — The pack format: writer, reader, merge and sparse index

- **Status:** open
- **Priority:** P1
- **Effort:** L
- **Source:** design A section 6.2 and design B section 6.2; both designs agree on immutable sorted packs, front coding, block compression and a sparse index. `docs/architecture.md` section 4.4 owns the contract.
- **Problem:** every dataset (names, domains, feed, reverse IP) is stored as packs, merged into higher tiers, and read by range from a Worker and from Node. No code writes or reads one. The byte layout is not fixed anywhere, and a consumer outside this repository must be able to read it.
- **Premise:**
  - MEASURED (design B M10 and DOM-008's premise): at 4,096 names a block, deflate level 9 costs 6.04 B a name, front coding alone 11.98 B. 7,948 blocks hold 32.5 million names. The 1,024 and 16,384 sizes cost 6.26 and 5.93 B.
  - READ design B section 6.2 and section 13: tiers above L0 add a source mask and per-source first and last day. Design B estimated 3 to 5 more bytes a name and did not measure it. This entry measures it.
  - READ design B section 6.2: a flat key list of the day pack would be about 1.4 MB at 1,024 names a block (31,792 blocks), about 0.7 MB at the default block size. A two-level index keeps a cold lookup at two small range reads.
  - READ `docs/architecture.md` section 4.4: parts of at most 1 GiB (a GHCR layer holds 10 GB and an upload lasts 10 minutes; mirror-archlinux measured 34 MB/s), `deflate-raw` blocks, a two-level `idx` layer whose top level holds the first key of every 64th index page. Optional layer `txt.gz`.
  - READ `docs/architecture.md` section 2: a merge takes the minimum of `t_first` and the maximum of `t_last` and unions the source masks, so a merge is idempotent. A record stores no count.
  - ⚠ Node's zlib output is deterministic only for one zlib build. A later Node release can change a compressed byte stream without changing its content. mirror-archlinux learned the same lesson with manifests: two writers must produce one digest, so it fixes every input of the manifest, `created` included.
- **Approach:**
  - **Package.** `packages/pack`. Writer API: `PackWriter` takes a dataset codec, a block size (default 4,096 records), a part limit (default 2^30 bytes), and emits parts plus the `idx` bytes. Reader API: `PackReader` takes an `idx` byte array and a `RangeSource` (`read(part, offset, length)`), and offers `get(key)`, `scan(lo, hi)` (async iterator) and `blockOf(key)`. The reader uses only Web APIs (`DecompressionStream`, `Uint8Array`, `DataView`), so one module runs in Node and in workerd. The writer may use `node:zlib` (`deflateRawSync`, level 9, default memory level). The merge `mergePacks(readers, codec)` is a k-way merge by key.
  - **Layout** (`docs/format.md` freezes these choices, with byte tables):
    - A part starts with 16 bytes: magic `DPK1`, `u8` version 1, `u8` dataset id (1 names, 2 domains, 3 feed, 4 reverse IP), `u16` records a block, `u16` part number, `u8` codec (1 `deflate-raw`, 2 `gzip`), 5 reserved zero bytes. The codec and the block size are fields of the header, so a reader never assumes them, and DOM-008's verdict (which may prefer 1,024 names a block or `gzip`) changes a default of the writer and no byte of the layout. Compressed blocks follow, back to back. A block never spans parts.
    - A record is `varint(shared)`, `varint(suffix_len << 2 | flags)`, the suffix bytes, then the dataset fields. `flags`: bit 0 exact, bit 1 wildcard. `shared` counts bytes shared with the previous key in the same block (zero for the first record of a block).
    - `names` fields: source mask as a varint (up to 64 bits), then for each set bit in ascending order `varint(first)` and `varint(last - first)`. `first` is in the source's precision unit: days since 2026-01-01 for a `day` source, seconds since 2026-01-01T00:00:00Z for a `second` source. `domains` adds an evidence list: a count, then for each entry `u8 tier`, `u8 basis`, `u8 source`, `varint(at)`, `u8 confidence`. `feed` has `varint(first_seen)` in seconds, the mask, `varint(basis bits)`, `u8 confidence` and `u8 flags` (provisional, suspect, corroborated, censored).
    - The `idx` layer starts with `DPKI`, the same version and dataset bytes, the block size and the counts. The top level lists, for each 64th entry, its first key (length prefixed) and its byte offset in the second level. The second level lists every block in order: first key (length prefixed), `u16` part, `u64` offset, `u32` compressed length, `u32` raw length, `u16` record count, `u32` CRC-32 of the raw block.
    - A lookup binary searches the top level (held in memory or in R2), range reads one second-level page (64 entries, about 4 KB), binary searches it, range reads the block, verifies its CRC, inflates it, and scans it.
  - **Codec interface.** A dataset registers `encodeRecord(prev, rec, out)` and `decodeRecord(prev, input)` and an `idxKey(rec)`. This entry ships the codecs of datasets 1, 2 and 3. DOM-043 registers dataset 4.
  - **Idempotence and integrity.** The writer sets the OCI annotation `dev.pkgforge.domains.sha256` to the SHA-256 of the decoded record stream (blocks concatenated before compression), not of the blobs. DOM-019's push tool treats an existing tag with the same decoded digest as present, even when the compressed bytes differ. `.node-version` pins the zlib build in CI. Every pack records the Node version in the annotation `dev.pkgforge.domains.writer`.
  - **Vectors.** `packages/pack/test/vectors/` holds three small packs as JSON (input records and the expected hex of the raw blocks and of the `idx`): three names and one source; wildcard and exact flags; two sources, one day and one second. ## DOM-018 — Verify a pack before it counts

- **Status:** open
- **Priority:** P1
- **Effort:** M
- **Source:** design B section 5.5 ("Verification before publish, the mirror's verify step, adapted") and design A section 8.2 and section 9; `docs/architecture.md` section 5.8.
- **Problem:** the root moves forward only after everything it names is verified. Without a verifier a bad segment (unsorted, truncated, an upper-case name, a volume a third of normal) reaches the live set and every later merge copies the defect.
- **Premise:**
  - READ `docs/architecture.md` section 5.8: decode the whole pack; check bytewise key order, uniqueness, charset, label length, no upper case, counts equal to the annotations; re-find 1,000 random keys with the reader the Worker uses; compare volume with the median of the last 7 days; check the PSL hash and the source's precision. No content regular expressions.
  - MEASURED (design A M2, design B M2; the sizes re-read 2026-10-27T09:34:52Z from the Hugging Face listing): THC's daily size was 843 to 986 MB in September, 984 and 957 MB on 10-01 and 10-02, 445 MB on 10-03, and 77 to 340 MB a day from 10-05, with no stated reason. A fixed band would have refused October. A THC day under 40% of the median of the last 7 accepted days is quarantined, not merged. A baseline that never moves would quarantine all 21 observed days from 10-05 on, so 3 consecutive days below the floor reset it (architecture section 5.8).
  - READ mirror-archlinux `docs/measurements.md` (2026-10-15): "a database cut to half its bytes gave 136 records and exit 0 from `db_records` before the fix in `db_tar`". The cause was a status read from the last stage of a pipe. The verifier must read the decoder's own status, and a cut pack must fail on length and count.
  - READ mirror-archlinux `docs/design.md` (rules table): "Every field of a database is checked against its grammar first ... A hostile name becomes a path, an option or a tag." Names here become keys and URLs.
  - MEASURED (design A M5): 4 of 38.5 million lines were themselves a public suffix and 0 failed the charset. Such names must refuse, not pass.
- **Approach:**
  - **Module.** `packages/pack/src/verify.ts`: `verifyPack(idx, source, expect)` returns `{ ok, errors, stats }`. `expect` holds the annotations: `count`, `bytes`, `dataset`, `source` ids, `psl` hash, `precision` per source, and `sha256` of the decoded stream.
  - **Checks, in this order.** (1) The part lengths sum to `bytes` minus the idx; every `idx` entry's offset and length fit its part. (2) Inflate every block; the CRC of each equals the idx; the record count of each equals the idx; the sum equals `count`. (3) Keys strictly increase bytewise across blocks; no key repeats. (4) Charset `[a-z0-9_.-]`, no empty label, labels at most 63 bytes, key at most 253 bytes, no upper case, and `fromKey(key)` passes `normalise` unchanged (uses DOM-015). (5) The SHA-256 of the decoded stream equals the annotation. (6) 1,000 keys drawn with a seeded generator, plus the first and the last, are found by `get()` through the same code path the Worker uses. (7) The PSL hash equals the pinned one. (8) Each source's precision equals `config/sources.json` (DOM-016): a `day` source has `last - first` in whole days. (9) `checkBand` of DOM-016 on `count` against the history of the same source: `ok`, `hold` (opens `anomaly-SOURCE`), or `quarantine`.
  - **CLI.** `scripts/verify-pack.mjs PATH...` for local part and idx files; later entries pass a GHCR source from `packages/ghcr`. Exit 0 ok, 1 a check failed, 2 could not run. The CLI prints `FAIL CHECK DETAIL` lines and never prints a key's content beyond 80 characters.
  - **Tests (red then green).** A pack with: two keys out of order; a duplicate key; an upper-case byte; a wildcard-only name; a pack cut to half its bytes; a pack cut at a block boundary (the count check catches it); a flipped byte (CRC); `count` annotation off by one; a wrong PSL hash; a `day` source with a time of day; 39% of the median volume (quarantine) and 60% (ok). Each fails alone and the clean pack passes.
- **Decision:** the volume rule is relative to the source's own history, `quarantine` below 40% for `day` sources and `hold` otherwise, with no absolute number, and a step change of 3 consecutive low days resets the baseline (`checkBand` of DOM-016 holds the rule; the verifier calls it). A quarantined segment is still pushed (raw data is kept) with the annotation `dev.pkgforge.domains.quarantine=1`, excluded from `new` computations, and an issue opens. The operator decides. The alternative of refusing to push loses data the operator ruled to keep.
- **Depends on:** DOM-017
- **Prove:** `node scripts/test.mjs packages/pack --name "verify"` passes: all 11 planted defects fail and the clean pack passes.
  - `node scripts/verify-pack.mjs packages/pack/test/vectors/clean.part.000 packages/pack/test/vectors/clean.idx` exits 0. The same command on `truncated.part.000` exits 1 and prints `FAIL length`. Read each exit code unpiped.
  - `node scripts/verify-pack.mjs --expect-count 1` on a pack of 2 records exits 1.

## DOM-021 — The domain table: exact first and last seen, and the provisional filter

- **Status:** open
- **Priority:** P1
- **Effort:** L
- **Source:** design A section 4.2 (registrable-domain record, evidence) and design B section 5.2 ("Domain ledger") and section 9; `docs/architecture.md` section 2, section 3.3 and section 5.8.
- **Problem:** "new" means no source observed the domain before. Some source must hold, for every registrable domain, its first and last seen per source, and answer "have we seen this before time T" for the thousands of domains an hourly job meets. A flat exact table is too big to scan an hour, and no code builds either structure.
- **Premise:**
  - MEASURED 2026-10-27 (design A M5): THC's daily dump holds 11.16 million registrable domains. 70.9% of 2026-10-26's registrable domains were absent from the three earlier days. The four-day union holds 36,993,405 registrable domains against a sum of 44,403,079.
  - MEASURED (design A M6, design B M4): OpenINTEL's `newly_registered_domain` carried 422,192 to 422,534 messages in 24 h. hagezi's `nrd7.txt` holds about 396,000 a day. So first-ever-seen registrable domains are 0.4 to 0.8 million a day.
  - READ design A section 6.3: a table of 100 to 250 million registrable domains at about 14 bytes is 1.4 to 3.5 GB. Both numbers are estimates. DOM-009 replaces them with the 54-day count.
  - READ design B section 5.2: a Bloom filter of registrable domains in R2, about 720 MB at 0.1% false positives for 400 million domains, OR-ed daily and rebuilt exactly each month. Events it flags are `provisional`, and the daily reconcile makes them exact.
  - READ `docs/architecture.md` section 5.1: the hourly job runs on Actions, where it can download the whole filter in seconds; a Worker cannot hold it (128 MB).
  - READ design B section 2.2 and section 9: name-level newness is censored for about 200 days. Domain-level newness from feeds with their own history (ISC, OpenINTEL, the lists) is not. A false positive of the filter means a new domain judged old. The daily exact pass repairs it.
  - READ `docs/architecture.md` section 2: `confidence` is `warming` while the corpus is younger than 90 days.
- **Approach:**
  - **Package.** `packages/ledger`. `aggregateToDomains(nameRecords)` turns name records into domain records with `packages/names` (reversed registrable key, per-source min first and max last, the `wild` flag dropped). Domain-level adapters emit domain records directly. Evidence entries (tier T1 `zone`, `rdap`; T2 `nrd-list`, `nrd-ct+rdap`; T3 `ct-first`) merge as a set of tuples. A `confidence` from OpenINTEL's confirmed topic passes through unchanged.
  - **Exact newness.** `firstSeen(rec)` is the minimum of `first` over sources, compared in the common unit (a day value counts as the start of its day). `exactNew(daySorted, baseReader)` merge-joins the day's sorted domain keys with the table of earlier tiers by key, using the idx to skip: a day key absent from every earlier tier is new on that day. This runs in the daily compaction on a runner. Reading the whole table (1.4 to 3.5 GB) at about 100 MB/s costs 15 to 35 seconds plus decode CPU. DOM-023 wires it.
  - **Provisional filter.** `packages/ledger/src/filter.ts` with the interface `MembershipFilter { has(hash), add(hash) }`. First implementation: a Bloom filter with 10 bits a key and 7 hashes (1% false positives), keyed by a 64-bit hash of the reversed registrable domain. A 250 million key table gives about 312 MB. It is built daily from the exact table, pushed to `state` as `ledger-filter-DATE` (a GHCR layer; every hot job pulls it once an hour), and paired with a small exact delta: a sorted array of the 64-bit hashes of domains first seen since the build (at most about 0.8 million, about 6.4 MB) in `state` as `ledger-delta`. The hourly job answers `has(h)` as `filter.has(h) or delta.has(h)`, adds new domains to the delta, and pushes the delta under the `state` guard of DOM-024. A new domain is `provisional: true` until the daily exact pass.
  - **Daily reconcile.** `reconcile(provisionalRows, exactNewSet)` returns the corrections: a domain judged old by a false positive that the exact join shows new gets a `feed` event in the day pack with `provisional: false`. The corrections are never lost: the day pack is built from the exact join, not from the hourly rows.
  - **Warming.** `corpusState(now, corpusSince)` returns `warming` while `now - corpusSince` is under 90 days, else `full`. The baseline is the THC backfill of DOM-029 (`corpus_since` 2026-09-01). The Common Crawl rank seed that design A section 4.3 floated is not adopted. A false "new" is labelled `warming`, which is honest, and a seed needs a source decision.
  - **Tests.** Idempotent merge; precision (`day` against `second`); a replay that builds the ledger from DOM-009's per-day files and checks 10 known domains; the measured false-positive rate on 1 million random absent keys (expect 0.8% to 1.2%); a domain added to the delta is found by the next hourly job; a false positive is repaired by `reconcile`.
- **Decision:** Bloom first, with the filter behind an interface. A binary fuse filter gives about 9 bits a key at 0.4% false positives and is immutable, so it needs the delta anyway. A Bloom filter is 40 lines, builds in one pass, and its 1% false positives only delay a "new" label by hours. Replace it only if the download size matters. The exact table decides every answer a caller keeps.

- **Prove:** `node scripts/test.mjs packages/ledger` passes.

## DOM-022 — The new-domain feed packs

- **Status:** open
- **Priority:** P1
- **Effort:** M
- **Source:** design A section 6.3 (`new-reg` day and hour files) and design B section 4 and section 6.3; `docs/architecture.md` section 3.3, section 7.3 and section 9. The operator's ruling 2 asks for windows of 1 h, 6 h, 12 h, 1 d and N days, on any suffix or parent.
- **Problem:** the feed answers "new domains in a window, under a suffix or a parent, with basis and confidence". The `domains` table is sorted by key, not by time, and has no confidence rules. A window query must read only the packs that overlap the window, scan only the key range, and sort by time without reading a whole day.
- **Premise:**
  - READ `docs/architecture.md` section 3.3: the `feed` dataset is keyed by reversed registrable domain and then `first_seen`. A record holds `first_seen`, the source mask, the basis bits, the confidence and the flags. About 15 to 30 MB a day [E] (0.3 to 0.7 million rows a day, design B section 6.3).
  - READ design B section 4 ("Confidence on domain rows"): `registered-confirmed` is an `oi-confirmed` confidence of at most 5, or a zone add, or an RDAP creation date in the window. `corroborated` is two different families within 48 h. `single` is one family. `suspect` is an `oi-nrd` event whose certificate is older than 7 days, excluded from the default feed.
  - MEASURED 2026-10-27 (design B M3, M5): `timestamp` is the emission time (receive minus timestamp at most 1 s) and `submission_timestamp` is the SCT time. 61.6% of events carried a certificate under 6 h old. 38% carried one older than 30 days, p90 at 144 days. Against Verisign RDAP, 25 of 25 `.com` and `.net` events with a fresh certificate were registered within 1 day (median 0.1 d). Of 25 with a certificate older than 30 days, 14 were not found and 11 were registered 35 to 5,157 days earlier. None was new.
  - READ design A section 3.1: the `confirmed_newly_registered_domain` topic adds `confidence` 1 to 10 (level 1 within 5 minutes of the RDAP date, level 10 within 18 to 24 hours). It mixes in zone rows (`ct_name: "zone_data"`, `cert_index: -1`, 9% of a sample).
  - READ `docs/architecture.md` section 4.5: a window of 1 h to 12 h reads segments and hour packs. A window of N days reads day packs and week packs where a week is whole.
  - Payload shapes for the fixtures. OpenINTEL: `{"domain":"creatorwide.com.","cert_index":167897527,"ct_name":"DigiCert 'Wyvern2026h2'","timestamp":1792069250,"submission_timestamp":1788554798.785}`. ISC rows: `domainname`, `ip` (an integer, present for about 32%), `firstseen` (a date), `score`, `scorereason`.
- **Approach:**
  - **Package.** `packages/feed`. Event record per `docs/architecture.md` section 3.3 and the `feed` codec of DOM-017. `buildFeedDay(domainRecords, exactNewSet)` makes the day pack from the exact join of DOM-021. `buildFeedHour(segmentRows, filter)` makes the hour pack with `provisional` rows.
  - **Confidence.** `confidenceOf(sourcesSeen, evidence)` returns `registered-confirmed`, `corroborated` or `single`, and the `suspect` flag, by the rules above. It lists its inputs in the row, so a caller can see why.
  - **Planner.** `planWindow(live, { t0, t1, suffix, under, kind })` returns the packs of the live set whose span overlaps `[t0, t1]`, and the key range of the `suffix` or `under` (from DOM-015 `rangeOfDescendants`, plus the parent point). A day-precision row is inside the window when its day overlaps it.
  - **Time order.** A `feed` day pack is key ordered. Sorting 0.5 million rows by time in a Worker costs too much CPU. The pack carries an optional extra layer `tidx`: an array of `(first_seen u32, ordinal u32)` sorted by time, about 4 MB for a day. `readFeed(live, window, range, { order, cursor })` reads one slice of `tidx`, maps the ordinals to blocks with the idx, and reads those blocks. A window of 12 h or less reads hour packs, which are small, and sorts them in memory. ⚠ `tidx` is a new optional layer. A reader that does not know it ignores it (`docs/architecture.md` section 11), and DOM-017's reader does.

A planner test for windows of 1 h, 6 h, 12 h, 1 d and 3 d with a live set of 6 segments, 12 hour packs and 2 day packs.
- **Decision:** a `tidx` layer on day packs, not a second pack sorted by time. A second copy doubles storage for the feed. `tidx` costs 4 MB a day and needs no second merge.

- **Prove:** `node scripts/test.mjs packages/feed` passes: every confidence rule, the planner windows, the `suffix` and `under` ranges (`np.com`, `co.uk`, `com`), and the time order with `tidx`.

It runs in the daily compaction matrix of DOM-023, by key range, so each job reads only its range of the base. A base of one year is about 100 GB. At 100 MB/s across 16 jobs that is about 1 minute of transfer each plus decode CPU.
  - **Censoring.** `censored(firstSeen, corpusSince)` is true while `firstSeen < corpusSince + CENSOR_DAYS`. `CENSOR_DAYS` is 200, in `config/names.json`. `confidence` on name rows follows `corpusState` of DOM-021. The pack annotation records `corpus_since` and `censor_days`.
  - **Pack.** Tag `newname-d-YYYYMMDD` in package `feed`, with `tidx` as in DOM-022. The reader `readNewNames(live, window, range, { order, cursor })` is exported from `packages/feed`. This entry also wires `kind=fqdn` of `GET /v1/new` (DOM-032) to it: the route answers 501 `not-implemented` for `fqdn` until this entry, and after it it reads these packs, returns `censored` in `flags` while the corpus is young, and lists `newname-d-...` tags in `meta.tiers_read`.
  - **Recurrence curve.** `scripts/measure/name-recurrence.mjs` uses the 54-day backfill of DOM-029 to print, for each lag from 1 to 50 days, the share of a day's names that also appear in the day that many days earlier. It writes `docs/research/measure/DOM-041/recurrence.json`. If the curve shows a plateau well below 200 days, record it. Do not change `CENSOR_DAYS` on fewer than 100 days of data.
  - **Tests.** A name seen on day 1 and again on day 40 is new only on day 1; a name whose first sight is inside the censor window is flagged; the join by key range equals the join over the whole base.
- **Decision:** an exact merge-join in the daily matrix, no name-level filter. A filter for 1 billion names at 10 bits is 1.25 GB and grows with the corpus, and its false positives would hide new names. The exact join reads only what a runner can stream, and it runs once a day.
- **Depends on:** DOM-021, DOM-032, DOM-038
- **Prove:** `node scripts/test.mjs packages/feed --name "newnames"` passes.

## DOM-043 — The reverse-IP packs

- **Status:** open
- **Priority:** P1
- **Effort:** L
- **Source:** the operator's ruling 7 of 2026-10-27: "serve the reverse ip/cname from the thc source from the ghcr mirror, not direct to thc itself". `docs/architecture.md` section 6.
- **Problem:** the mirror of THC's monthly database (DOM-042) holds 6.36 billion `ip,name` lines as gzipped CSV chunks in GHCR. A reverse lookup needs them sorted by address, so a range read answers one address or a CIDR. The file is not sorted by address and is too large for a Worker. A runner must build the index.
- **Premise:**
  - MEASURED `curl -sSL -r 0-1048575 -o head1m.csv.gz 'https://huggingface.co/buckets/IP-THC-ORG/Datasets/resolve/2026/10/rdns-sept.csv.gz?download=true'` 2026-10-27T08:21:59Z, then `gzip -dc | head -c 3000000`: 72,834 lines, every line two comma separated fields `ip,name`, no header. IPv4 and IPv6 both appear (IPv6 from line 5,486, for example `2a00:c00:f060:1::204,staging.ext.login-sg.isso.intranet.db.com`). The order is not by address (`sort -c` failed at line 2). 41,973 distinct addresses in 72,834 lines; 190.0.0.1 has 4,993 lines. The sample averages 41.2 bytes a line. 252 GB over 6.36 billion records is 39.6 bytes. There is no third column and no CNAME target.
  - MEASURED `curl -sSI` of the September file 2026-10-27T08:21:52Z: 37,046,639,482 B, `accept-ranges: bytes`, `Last-Modified: Fri, 02 Oct 2026 16:25:18 GMT`. Bucket listing 2026-10-27T08:25:12Z: `2026/9/rdns-aug.csv.gz` 36,029,717,282 B, `2026/10/rdns-sept.csv.gz` 37,046,639,482 B. So 5.82 B a record compressed.
  - READ `https://ip.thc.org/docs/bulk-data-access` (2026-10-27T08:21:38Z; a request needs a browser User-Agent, as DOM-010 records): September 2026, released October 4, 6.36 billion records, CSV 35 GB compressed and 252 GB uncompressed.
  - READ `docs/research/web-pkgforge-2026-10-27/ct.md` section 1: THC's live reverse lookup returned 92,770 rows for 1.1.1.1, 45,606 for 8.8.8.8, 19 for 140.82.112.3, 15 for 89.58.57.239. Its live API returned 0 rows for IPv6. The dump holds IPv6.
  - READ mirror-archlinux `docs/measurements.md`: a runner starts with about 87 GB free (14 GB guaranteed), `scripts/debloat-runner` raised that to 120 GiB in 45 s. A job lasts at most 6 hours. A matrix has at most 256 jobs and the organisation runs 20 at once.
  - READ `docs/architecture.md` section 6: the raw CSV chunks are in package `obs` (DOM-042). The packs go to package `rev`, tag `rev-m-YYYYMM`. A query reads the newest month by default.
  - Estimate [E]: the pack costs 3 to 5 B a record, so 20 to 32 GB a month. This entry measures it on the September file.
- **Approach:**
  - **Codec.** Register dataset id 4 in `packages/pack` (the codec interface of DOM-017). A record is one `(address, name)` pair. Addresses of one family go to separate parts: family byte 4 or 6, then the address bytes (4 or 16, big endian). Sort order is `(family, address, name key)`, where the name key is the reversed-label form from DOM-015, so names that share a registered suffix share a prefix. The address part is coded by shared prefix with the previous address. The name part is front coded against the previous record's name key even when the address differs. The `idx` key of a block is `(family, address)` and a flag marks a block that continues an address of the previous block. A lookup for one address finds the first block whose last address is not below it and reads blocks until the first address is above it. A CIDR is the range from its first to its last address.
  - **Build.** `.github/workflows/rev-monthly.yml`, job `rev`, `packages: write` and `contents: read`, `timeout-minutes: 360`. It reads the raw chunks from the GHCR mirror (not from THC): `cat chunk.000 chunk.001 ...` into `gzip -dc`. Stage A converts each address to a fixed-width hex key (8 characters for IPv4, 32 for IPv6) and writes lines to bucket files by family and first byte. Stage B sorts each bucket with `LC_ALL=C sort -u -S 8G -T DIR`, and encodes it into parts of at most 1 GiB. Stage C writes the manifest (parts plus `idx`), verifies (DOM-018), pushes `rev:rev-m-202609`, and calls `root-promote.yml`.
  - **Two plans, measure both.** (a) One job: stream once, partition to disk compressed with `gzip -1` (about 37 to 60 GB), sort and encode every bucket. Needs `debloat-runner` and about 3 to 5 hours [E]. (b) A matrix of 8 jobs, each streaming the whole file (37 GB at the rate DOM-010 measured, plus about 15 to 17 minutes of `gzip -dc` for 252 GB on one core) and keeping the first-byte range it owns. With `max-parallel` 4 it needs about 2 to 3 hours [E]. Record both times in `docs/research/measure/DOM-043/result.json` and choose.
  - **Counts.** Stage A counts lines per bucket. The sum plus the duplicates that `sort -u` dropped must equal the whole-file count of DOM-010's scan. The verifier recounts records from the packs.
  - **Months.** Build August first (the smaller test), then September. Each month is its own pack set. No merge across months.
  - **Reader.** `packages/pack/src/rev.ts` offers `lookupIp(reader, ip)` and `lookupCidr(reader, cidr, cursor)`. It returns the names in key order with a cursor. It computes `apex_domain` and `tld` at query time with `packages/names` and the pinned PSL. The data holds no organisation, country or ASN.
  - **Script.** `scripts/rev/lookup.mjs --month 2026-09 --ip 190.0.0.1 --count` for gate (b).
- **Decision:** the pair stream as records, not one record per address with a name list. A popular address holds 92,770 or more names. A list record would exceed a block and force a second structure. Pair records make paging, CIDR ranges and front coding the same code path as every other dataset.
- **Depends on:** DOM-017, DOM-042
- **Prove:** `node scripts/test.mjs packages/pack --name "rev"` passes: IPv4 and IPv6 order, a block that continues an address, a CIDR range, name front coding across addresses.
  - After the August run: `node scripts/rev/lookup.mjs --month 2026-08 --ip 190.0.0.1 --count` prints a count of at least 4,000.
  - After the September run: `node scripts/rev/lookup.mjs --month 2026-09 --verify-total` prints `OK records N dropped D scan S` where N plus D equals S from DOM-010's result, and exits 0. Read the exit code unpiped.
  - `curl -sS -H 'Authorization: Bearer QQ==' -H 'Accept: application/vnd.oci.image.manifest.v1+json' https://ghcr.io/v2/pkgforge-dev/domains.pkgforge.dev/rev/manifests/rev-m-202609 | jq -r .artifactType` prints `application/vnd.pkgforge.domains.pack.v1`.

## DOM-053 — Rebuild R2 from GHCR and serve with R2 empty

- **Status:** open
- **Priority:** P2
- **Effort:** S
- **Source:** design A section 8.1 and design B section 8 ("R2 down", "GHCR is the only copy of the truth"); `docs/architecture.md` section 4.9 and section 8.
- **Problem:** the design says everything in R2 can be rebuilt from GHCR and that the service answers with R2 empty or down. Nothing proves it. An untested cache that the service secretly depends on is the failure this drill catches.
- **Premise:**
  - READ `docs/architecture.md` section 8: "R2 down: R2 errors; reads GHCR; none". `x-domains-cache` says what answered (`hit`, `r2`, `ghcr`, `mixed`) and never names a layer the request did not use.
  - READ `docs/architecture.md` section 4.9: R2 holds `root/`, `idx/`, `hot/`, `blk/`. Lifecycle rules expire `blk/` after 14 days and `hot/` after 7 days, so a quiet period empties them on its own.
  - READ design B section 8: R2 down means windows under 72 hours answer from GHCR feed packs, stale by up to an hour, with `degraded: true`.
  - A drill must not damage the live cache. Cloudflare's wrangler has no bulk object delete, and the live bucket stays untouched. So the drill runs a second copy of the Worker against an empty bucket.
- **Approach:**
  - **Drill Worker.** Deploy the same `apps/api` build under the name `domains-drill` with `workers_dev = true` and `preview_urls = false`, bound to an empty bucket `domains-drill` (`wrangler.drill.toml` next to `wrangler.toml`, same code, other names). It has no custom domain. It is a temporary measurement Worker: `SECURITY.md` keeps `workers_dev = false` for every Worker that serves callers and names this drill and the probe of DOM-061 as the two that run on workers.dev, for their life only. The drill holds no data of its own (its bucket is a cache of public data) and is deleted at the end of this entry. The bucket `domains-drill` is a second R2 bucket beside the one cache bucket `domains-pkgforge-cache` (architecture section 12); it never holds more than the cache bound of 5 GB.
  - **Script.** `scripts/drill/r2-empty.mjs --base https://DRILL_HOST --compare https://domains.pkgforge.dev`. It sends 20 fixed requests (`/v1/index/latest`, `/v1/new?since=1d&suffix=com.np`, `/v1/new?since=1h`, `/v1/subdomains/np.com` when DOM-039 exists, `/v1/ip/190.0.0.1` when DOM-044 exists, a dump listing) to both hosts. It asserts equal bodies after removing the `meta.cache` fields, `x-domains-cache` of the drill is `ghcr` or `mixed` on the first pass, no 5xx, and p95 under 10 s cold. It then waits for the drill's cron warmer, sends the same requests again, and asserts the cache header changes to `r2` or `hit`.
  - **Rebuild.** After the first pass, run the drill Worker's warmer once and list the bucket: `idx/`, `root/` and `hot/` exist, and `blk/` fills with reads. Record the object counts and bytes in `docs/research/measure/DOM-053/result.json`.
  - **Clean up.** Delete the drill Worker and its bucket.
- **Decision:** a second Worker and an empty bucket, not deleting objects from the live bucket. Deleting live objects is unrecoverable damage to a cache for a test, and the second Worker proves the same thing.
- **Depends on:** DOM-031
- **Operator:** run `npx wrangler@4.150.0 whoami` first and record the account name it prints in this entry's Closed line. Then, with the local wrangler login: `npx wrangler@4.150.0 r2 bucket create domains-drill`, then `npx wrangler@4.150.0 deploy --config wrangler.drill.toml` from `apps/api`.
